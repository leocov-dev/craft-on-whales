# Drizzle schema translation notes

`src/db/schema/*.ts` was generated by diffing the ACTUAL post-migration
SQLite schema (dumped via `sqlite_master`, not hand-replayed from
`src/db/migrations/*.ts`) against Drizzle's `sqlite-core` builders. Two
known simplifications versus the legacy schema, called out so they aren't
mistaken for oversights:

1. **`users.username` loses its `COLLATE NOCASE`.** Drizzle's `sqlite-core`
   text column builder has no first-class collation option. The generated
   migration will need a manual `ALTER`/recreate step (SQLite can't add
   collation to an existing column) — add a raw `sql` migration for this
   once `drizzle-kit generate` produces the initial migration, before this
   schema is used against real data.
2. **`CHECK` constraints are not expressed** (e.g. `servers.update_policy IN
   ('manual','notify','auto')`, `chat_commands.action IN (...)`). These are
   enforced by zod validation at the API boundary instead, matching how
   every other input already gets validated in this codebase — not a
   regression in practice, just not enforced a second time at the DB layer.

`drizzle-orm`/`drizzle-kit` are pinned to the `1.0.0-rc` prerelease line
specifically because the stable 0.45.x release has no `node:sqlite` driver
(`drizzle-orm/node-sqlite`) — only `better-sqlite3` and friends, which would
reintroduce a native dependency this codebase deliberately avoids (see
`docs/architecture.md`). Re-pin to a stable 1.x once it ships.

**Driver gotcha**: `drizzle-orm/node-sqlite`'s `drizzle()` only picks up an
existing `node:sqlite` `DatabaseSync` instance when passed as
`drizzle({ client: sqlite })`. Passing the instance directly
(`drizzle(sqlite)`) silently opens a *second*, separate `:memory:` database
instead of erroring — confirmed by a manual smoke test before this schema
was written. `DbModule`'s provider must use the `{ client }` form.

**`schema` config key gotcha**: this RC line's `DrizzleSQLiteConfig` type
`Omit`s `schema` entirely — the plain-table-map `schema` option from stable
drizzle (which powers `db.query.*` relational queries) has been replaced by
a separate `relations()`/`defineRelations` API not yet adopted here. Passing
`drizzle({ client, schema })` type-checks into a confusing relational-config
constraint error rather than a clean "unknown property." `DbService` calls
`drizzle({ client })` with no schema and exposes only the SQL-like builder
(`db.select()/insert()/update()/delete()` against the `schema/*` table
exports) — matches the plan's "TS-first, SQL-like query builder" framing
anyway, so `db.query.*` was never a requirement.

**Node 22 is not enough** — even with `--experimental-sqlite`, Node
22.13.1's `node:sqlite` throws `stmt.setReturnArrays is not a function`
inside this RC driver's session code. `node:sqlite` only grew the API
surface this driver needs in Node ≥24 (matches `package.json`'s
`engines.node` already). Verify with Node ≥24 (`brew install node`, not the
repo's pinned older runtime) — a stray Node 22 `node`/`npx` earlier on
`$PATH` produces this exact confusing error.

**`app.init()` gotcha**: `NestFactory.create()` does *not* run
`onModuleInit` lifecycle hooks — those only fire on an explicit
`app.init()` (or the `app.listen()` call, which calls it internally).
Migrations invoked from `main.ts` between `create()` and `listen()` (per
the plan: "explicit Drizzle migration run" before `app.listen()`) need an
explicit `await app.init()` first, or `DbService.db` is still `undefined`
when `runMigrations()` reads it — confirmed by a `TypeError: Cannot read
properties of undefined (reading 'session')` boot-test failure before this
was added.
